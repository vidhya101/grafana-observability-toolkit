How to Read (and Write) a PromQL Query

If you've never written one of these, start here. Every query on this page is built from the same handful of pieces, in the same order — once you can name the pieces, you can write your own.

1. Anatomy of a query

Here's a real one from this page (row 6b — the OOM early-warning check), colored piece by piece:

container_memory_working_set_bytes / on(pod,namespace,container) kube_pod_container_resource_limits{resource="memory"} > 0.9
Metric name — which time series to pull
Label matcher {...} — filters which series of that metric
Operator — vector-match (on()) or comparison (>)

2. Reading it left to right

1
container_memory_working_set_bytes

Start with a metric name. On its own, this returns every time series for it — one per container, across every pod, in every namespace. Too much to be useful yet.

2
kube_pod_container_resource_limits{resource="memory"}

The {resource="memory"} part is a label matcher — it narrows a metric down to just the series where that label equals that value. Without it you'd get CPU limits mixed in with memory limits.

3
a / on(pod,namespace,container) b

Dividing one metric by another only works if Prometheus knows how to pair up matching series between them — on(pod,namespace,container) says "match rows where these three labels are identical." This is the single most common thing beginners get stuck on.

4
> 0.9

The comparison at the end turns a number into a yes/no. Drop it and you get the raw ratio for every container, as a graph; keep it and you get only the containers currently over 90% — exactly what you'd wire into an alert.

3. The evaluation loop — what for: actually does

Prometheus doesn't run a query once — it re-runs every query and every alerting rule on a fixed clock (evaluation_interval, usually 15s–1m). That repeating tick is the "loop." An alert rule's for: duration says how many consecutive ticks the condition has to stay true before it actually pages you:

alert: FailedSchedulingEvents expr: sum(count_over_time({job="k8s-events"} | json | reason="FailedScheduling"[5m])) > 0 for: 1m
t=0s

Condition first becomes true. State flips to pending — visible in Prometheus's UI, but nothing pages yet.

t=15s

Next tick. Still true → stays pending. If it had gone false here, it would silently reset to inactive and nothing would ever fire — this is what stops a single blip from paging anyone.

t=60s

The full for: 1m has now elapsed with the condition true the entire time → state flips to firing and Alertmanager is notified.

4. Comparison & boolean logic

OperatorExampleMeaning
==reason="FailedScheduling"Exactly equal.
!=kube_replicaset_status_replicas != kube_replicaset_spec_replicasNot equal — the classic "actual doesn't match desired" pattern.
=~reason=~"FailedMount|FailedAttachVolume"Regex match — true if the label matches any of the alternatives.
!~fstype!~"tmpfs|overlay"Regex non-match — excludes anything matching the pattern.
> < >= <=node_load1 / count(...) > 1Numeric comparison, same as any language.
anda and on(pod) bKeeps only series present in both sides — a set intersection, used constantly to join two metrics together.
orcount(x) or vector(0)Falls back to the right side only when the left side has zero results — the exact trick this whole page uses so a healthy stat panel shows "0" instead of going blank.
unlesscount(kube_pod_container_info) unless on(pod,namespace,container) kube_pod_container_resource_requestsKeeps only series from the left that have no match on the right — "find things missing a corresponding row."

5. What the colored dot next to every row means

Every diagnostic row below carries a severity dot — click a table's first column header to sort by it, or use the "In an active incident" filter chips at the top of the page to instantly narrow the whole reference to just one level.

Critical — active failure or outage; stop and act
Warning — degraded or trending toward failure; investigate soon
Info — context, inventory, or a diagnostic tool rather than an alert condition

Part Seven

Function Cheat Sheets

Not "run this exact query" rows — these are the building blocks. Understanding these six PromQL functions and five LogQL patterns covers the vast majority of what you'll ever need to write from scratch.

PromQL Functions

FunctionExampleWhat it doesGotcha
rate() vs irate()rate(x[5m]) vs irate(x[5m])Both compute per-second rate of a counter; rate averages across the whole window, irate uses only the last two data points.Use rate for alerting/dashboards (smoother); irate only for fast-moving graphs where you want to see spikes instantly.
increase()increase(x[15m])Total absolute increase of a counter over the window (rate × window size).Resets to zero on a counter restart — a pod restart can look like a dip, not a real drop.
histogram_quantile()histogram_quantile(0.95, sum(rate(x_bucket[5m])) by (le))Estimated percentile from a _bucket histogram series.Requires the metric to actually be a histogram (has a le label) — doesn't work on a plain gauge/counter.
topk() / bottomk()topk(5, sum(x) by (pod))The 5 highest (or lowest) series by value.Great for "what's the worst offender" panels — remember it re-evaluates per step, so the top-5 set can shift over a graph's time range.
label_replace()label_replace(x, "short_pod", "$1", "pod", "(.*)-[a-z0-9]+")Adds/rewrites a label using a regex capture.Joining two metrics whose label values don't quite match (e.g. stripping a hash suffix) before an on() match.
Vector matching: on() / group_left()a * on(pod,namespace) group_left() bJoins two metrics on shared labels; group_left allows a many-to-one match, carrying extra labels from the right side.Every "which pod belongs to which deployment" query on this page uses this — get the match labels wrong and you silently get zero results, not an error.
absent()absent(up{job="x"})Returns 1 only if the series doesn't exist at all.The only way to alert on "this should exist and doesn't" — a target that's merely down still has a series (up == 0).
